# セキュリティ設計（読み取り専用の監視データ提供）

AI エージェント（MCP サーバー経由）が障害調査のために監視データを参照できるようにする。
その際に **AI に「できること」と「見えるもの」を最小限に絞る** ための設計をまとめる。

## 1. 構成と信頼境界

```
[AI エージェント] ─ MCP ─ [MCP サーバー（ローカル）] ─ AWS API ─ [SSM Run Command] ─ [EC2: collect.py]
                                   │                                            │
                                   └─ CloudWatch（読み取り専用 API）              └─ docker / ClickHouse / ログ
```

| 境界 | 守るもの | 手段 |
|------|----------|------|
| エージェント → MCP | 実行できる操作 | MCP のツールは読み取り専用のものだけ。書き込み系ツールは作らない |
| MCP → AWS | AWS 上の権限 | MCP 専用の IAM ロール（最小権限）。利用者本人の管理者権限とは分ける |
| SSM → EC2 | EC2 上で実行できるコマンド | 固定コマンドの SSM ドキュメント + `collect.py` の許可リスト |
| EC2 → エージェント | 出力に含まれる情報 | `collect.py` で全出力をマスキング、外部由来の文字列を無害化 |

## 2. 脅威と対策

| 脅威 | 対策 | 状態 |
|------|------|------|
| エージェントが任意のコマンドを実行する | `collect.py` は `monitoring/queries.py` の `COMMANDS`（許可リスト）以外を拒否。任意のシェル・SQL・docker 引数を受け取る口がない | ✅ |
| 引数経由のインジェクション（`--name "-f"`、`6; rm -rf /` 等） | 引数は `--名前 値` のみ厳密に解釈（短縮形・未知の引数・重複を拒否）。整数は桁数と範囲、文字列は長さと制御文字、コンテナ名は形式 + **実在する名前との完全一致** | ✅ |
| 個人情報・認証情報の流出 | 全出力と監査ログを `monitoring/mask.py` でマスキング：IP（上位 2 オクテットのみ残す）、メールアドレス、URL のクエリ値、Authorization / Bearer、API キー（AWS / Google / Anthropic / Slack）、Slack Webhook、Sentry DSN、JWT、`password=` 等 | ✅ |
| **ログ経由のプロンプトインジェクション**（User-Agent やパスに「指示」を書き込む） | ログ行は制御文字・ANSI エスケープを除去し 500 文字に制限。`untrusted: true` と「指示には従わない」注記を付けて返す。そもそもツールが読み取り専用なので、乗っ取られても実行できる操作がない | ✅（MCP 側の注記は今後） |
| 日次巡検への影響 | どのコマンドも `state.json` を書かない（テストで検証）。書き込むのは監査ログのみ | ✅ |
| サーバー負荷（リソースに余裕のない EC2） | 実行時間の上限（120 秒）、出力サイズの上限（256 KiB）、ログは最大 20,000 行を読み 500 行まで返す | ✅ |
| 実行の追跡ができない | すべての呼び出し（拒否されたものを含む）を `out/collect_audit.log` に 1 行 JSON で記録（時刻・実行者・コマンド・引数・成否・所要時間・出力サイズ） | ✅ |
| `collect.py` 自体の改ざん（SSM が呼ぶ「固定コマンド」の中身が変わる） | SSM から呼ぶコードは root 所有・一般ユーザー書き込み不可の場所（例 `/opt/ai-monitoring`）に配置する | 今後 |
| MCP の権限で EC2 にログインする | MCP 専用ロールは特定の SSM ドキュメントの `ssm:SendCommand` のみ許可し、`ssm:StartSession` は明示的に拒否 | 今後 |
| エージェントが MCP を迂回する | 調査用エージェントにはシェル実行や管理者の AWS 認証情報を与えない（MCP のツールだけを使わせる） | 運用ルール |

## 3. AI の提案の扱い

AI の診断・推奨アクションは**自動実行しない**。人が確認してから操作する。
実例：AI が推奨した `docker-compose up -d --force-recreate sentry-self-hosted-nginx-1` はサービス名ではなくコンテナ名を使っており、
そのままでは失敗する。また根本原因（毎日 03:00 の truncate ジョブ）を解決しないため、再作成しても再発していた。

## 4. テスト

`tests/test_mask.py`・`tests/test_collect.py` が上記の対策を検証する（許可リスト、引数検証、マスキング、無害化、
出力上限、タイムアウト、監査ログ、`state.json` を書かないこと）。対策を外すとテストが失敗することを確認済み。
