# AI 運用モニタリング支援 — 計画書 / プロジェクト構成

> 目的：AI を用いて**この EC2 上に自前ホストした Sentry + PostHog プラットフォーム**を定期的に点検し、その Web / バックエンドサービスの正常稼働を保証する。「Slack アラート・ユーザー報告を待つ受動的運用」から「能動的に問題を発見し、原因を特定し、対処案を提示する運用」へ転換する。社内 task「AI を活用した開発・運用メンテナンス効率化」に対応 —— 単一プロジェクトで 2 つ以上のデータソースを統合し、AI が障害要約・改善提案を含むレポートを自動生成する。

---

## 1. 背景と目的

### 運用対象

この EC2 は**自前ホストの可観測性プラットフォーム**（Sentry + PostHog、および各 Docker コンテナ：web / snuba / taskworker / clickhouse / kafka / redis / postgres 等）を稼働させている。運用責務は**これらのプラットフォームサービスを継続的に正常稼働させること**。

> 注意：Sentry に集まる issues（GRAPE-ANDROID / GRAPE-IOS のモバイルクラッシュ）は **アプリ開発チーム**が見る内容であり、「ユーザーのアプリが落ちたか」を答えるもの。「プラットフォームが健全か」とは別問題であり、本プロジェクトの運用上の主眼ではない。

### 現状（改善前）

- **リソースアラート**：ディスク / メモリ逼迫時に Slack 通知。
- **サービス異常**：Web が開けないとユーザーに報告されて初めて気づくことが多い。
- **調査方法**：通知後、手動で log / `docker` 状態を追って原因特定。

課題：受動的・後手・「プラットフォーム全体の健康状態」を俯瞰する統一的視点の欠如。

### 目的（改善後）

1. **能動的な健康点検**：コンテナ・ホストリソース・Web 可用性を定期自動チェック。報告を待たない。
2. **原因特定の支援**：異常（コンテナ停止、OOM、ディスク逼迫、Web 5xx）を AI が想定原因分析。
3. **対処提案**：AI が具体的アクションを提示し MTTR を短縮。
4. **拡張可能**：ローカル点検が動いた後、CloudWatch 等を段階的に追加。

## 2. データソースと役割（運用優先度順）

| データソース | 答える問い | 優先度 / 役割 |
|--------------|-----------|--------------|
| **ローカル稼働シグナル**（docker + /proc + Web 疎通） | コンテナは生きているか？リソースは足りるか？Web は通じるか？ | **最優先**（第1ステップの中核、データは全てローカル） |
| **CloudWatch** | ホスト/インスタンス層の指標、より詳細な履歴とアラート | 第3ステップで接続（2 つ目のソース） |
| Sentry（取り込み健全性） | Sentry は正常にデータを受信し続けているか（イベント量の急減＝パイプライン障害） | 任意・間接的な健康シグナル |
| Sentry（エラー内容） | アプリが何のエラーを出したか | **運用の主眼ではない**、アプリチームへ |

> task 要件「2 つ以上のデータソース統合」→ 達成経路は **ローカル稼働シグナル + CloudWatch**。

## 3. 全体アーキテクチャ

```
[cron による定期起動（短命プロセス）]
        │
        ▼
[収集層] ローカルシグナル：docker コンテナ状態 + ホストリソース(/proc) + Web 疎通
        │   · データは全てローカル、外部 API token は基本不要
        │   · 軽量収集、メモリ有界
        ▼
[ルール層] 確定的な閾値判定で先にアラートを算出（ディスク/メモリ/コンテナ/Web）
        │
        ▼
[AI 層] 健康スナップショットを LLM へ → 総合ステータス / 原因分析 / 対処提案
        │
        ▼
[出力層] 健康スナップショット JSON + Markdown レポート → EC2 に保存
            · 後続で拡張：Slack / メール / Web ダッシュボード
```

**レイヤ分離**：収集・ルール・AI・出力を独立させ、データソースや出力方式の変更は該当層のみ修正。

## 4. 段階的ロードマップ

### 第1ステップ ✅（完成）— プラットフォーム健康点検（`platform_health.py`）

- 3 種類のローカルシグナルを収集：
  1. **コンテナ健全性**：docker 各コンテナの status / health / 再起動回数 / OOM。中核コンテナ（sentry/posthog…）に ★。
  2. **ホストリソース**：ディスク、メモリ、swap、load（/proc と statvfs を読む、依存ゼロ）。
  3. **Web 可用性**：Sentry / PostHog の URL へ HTTP 疎通（ステータスコード + レイテンシ）。
- まず確定的ルールでアラートを算出し、次に AI が「総合ステータス + 異常 + 想定原因 + 推奨アクション」レポートを生成。
- 特性：依存ゼロ、短命プロセス、成果物は極小で自動クリーンアップ。
- 状態：EC2 で `sudo -E python3 platform_health.py --dry-run` を実行し収集を確認する段階。

### 第2ステップ — 点検の深化 + トレンド

- ✅ Web 疎通を `/_health` 深度ヘルスチェック端点へ。
- ✅ コンテナ再起動は累計でなく「前回巡検からの増分」で判定（`out/state.json` に前回値を保持）。
- ✅ コンテナ別メモリ / swap 使用量（cgroup 直読）と swap 換ページ速度を収集し、AI が原因コンテナを特定できるように。
- ✅ ディスク増加速度（GB/日）と閾値到達予測日を算出し AI に渡す（実測 +1.3GB/日、85% 到達は 2026-12 上旬見込み）。
- ✅ RestartCount に現れない再起動（手動 restart / 再作成 / 定期ジョブ）を起動時刻の変化で検出。
- ✅ 換ページの無い swap 残留はアラートを 1 段階下げ、ノイズ化を防止。
- レベル別アラート：CRIT 時のみ通知。

### 第3ステップ — CloudWatch 接続（task の 2 ソース達成）— 🚧 実装済み・IAM 権限待ち

- ✅ インスタンス層の指標（CPU、ネットワーク、EBS IO・突発余額、CPU credit、状態チェック）と本インスタンスの CloudWatch アラームを取得（aws CLI 経由、依存追加なし）。
- ⏳ 実行にはインスタンスロール `posthog-sentry-ec2-role` に `iam/cloudwatch-read-policy.json` の権限付与が必要（2026-10 時点で未付与）。
- AI による横断関連付け：ローカル症状 ↔ クラウド指標（例「taskworker が繰り返し OOM ↔ インスタンスメモリが高止まり」）。
- task 要件「2 つ以上のデータソース統合」を達成。

### 第4ステップ（任意）— 出力と運用化

- レポート配信：Slack / メール / 簡易 Web ダッシュボード。
- 閾値とサイレンス方針、当番通知 など。

### 派生（運用の主眼外）— Sentry エラー要約（`sentry_report.py`、本リポジトリ未収録）

Sentry issues 要約スクリプト（別管理で、本リポジトリには含まれていない）。「直近 24h にどのアプリエラーがあったか」を出力。**この系統はアプリチーム向け**で、そのまま引き渡せる。本運用プロジェクトの主線ではない。

## 5. リソースとコストの制約（重要）

リソースに余裕の少ない EC2（4 コア / メモリ 16G、Sentry/PostHog の 37 コンテナが大半を占有；ディスク 322GB 中約 65%、swap 数 GB 使用 — 2026-10 実測）上で動作させるため：

- **短命プロセス**：cron 起動、実行後即終了、常駐しない。ピークメモリ数十 MB。
- **重い依存ゼロ**：標準ライブラリのみ。pip 不要、venv 不要、追加ディスク消費なし。
- **成果物は極小**：スナップショット JSON + Markdown（各数 KB）のみ保存、N 日後に自動削除。
- **ローカル収集は穏当**：docker inspect / /proc 読み取り / 数回の HTTP 疎通で、プラットフォームサービスへの負荷は無視できる。
- **ハードガード**：cron で `systemd-run -p MemoryMax=256M -p CPUQuota=50%` + `nice`/`ionice`。

**コスト**：EC2 本体は料金上がらず；唯一の新規費用は **LLM API 呼び出し料**（`AI_PROVIDER` で Gemini / Claude を切替、既定は Gemini）（小さな健康スナップショットのみ送るため 1 日数セント程度）；`--dry-run` では発生しない。

## 6. データとプライバシー

- 本プロジェクトが収集するのは**プラットフォーム稼働/健康データ**（コンテナ状態、ホストリソース、Web ステータスコード）であり、**ユーザーの個人情報や端末情報は含まない**。
- 唯一留意すべき派生 `sentry_report.py`：そのエラータイトルに PII が意図せず含まれ得る。利用する場合は Sentry の **Data Scrubbing** を有効化し、送信前に `mask_pii()` を行う。運用主線はこの問題に該当しない。

## 7. コード管理とデプロイ

- **本リポジトリ**：GitHub / GitLab（または社内 Git）でホストし、バージョン履歴・協業・レビュー・バックアップの「正」とする。
- **EC2**：デプロイ/実行ターゲットとしてのみ利用。`git clone` + `git pull` 後に cron で実行。**EC2 をリポジトリの本体にしない**。
- **絶対にコミットしない**：`.env`（API key）、`out/`（実行成果物）—— `.gitignore` 参照。
- **復旧**：EC2 障害時もインスタンス再作成 + `git clone` + `.env` 設定で運用復旧。
