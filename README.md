# AI 運用モニタリング支援（Sentry + PostHog）

> 自前ホストの **Sentry + PostHog プラットフォーム**（EC2 上の Docker、37 コンテナ）を 1 日 1 回点検し、
> 複数のデータソースを突き合わせて **AI が異常の要約・想定原因・対処案** を出す。状態が変わったときだけ Slack に通知する。
>
> 社内 task「AI を活用した開発・運用メンテナンス効率化」の成果物。詳細な仕様（収集項目・閾値・AI への入力）は [SPEC.md](SPEC.md) を参照。

---

## 1. 背景と目的

### 運用対象

この EC2 は**自前ホストの可観測性プラットフォーム**（Sentry + PostHog、および web / snuba / taskworker / clickhouse / kafka / redis / postgres 等のコンテナ）を稼働させている。
運用責務は**これらのプラットフォームを継続的に正常稼働させること**。

> Sentry に集まる issues（GRAPE-ANDROID / GRAPE-IOS のモバイルクラッシュ）はアプリ開発チームが見るもので、「プラットフォームが健全か」とは別の問題。本プロジェクトの対象外。

### 改善前の課題

- **リソース通知**：既存の Slack bot（`slack_alert.sh` / `slack_alert_http.sh`）がディスク・メモリ・swap・nginx 5xx を閾値で通知。
- **気付くのが遅い**：Web が開けないことをユーザーからの報告で知ることがある。
- **調査が手作業**：通知を受けてから、ログや `docker` の状態を手で追って原因を探す。
- **全体像がない**：閾値ごとのバラバラな通知で、「プラットフォーム全体として健全か」「この先どうなるか」が分からない。

### 目的

1. **能動的な点検**：コンテナ・ホスト・Web・クラウド指標を定期的に自動チェックする。
2. **原因の推定**：複数のデータソースを突き合わせ、AI が想定原因を示す。
3. **対処案と予測**：具体的なアクションと、容量到達などの見込み時期を示し、先回りできるようにする。
4. **ノイズを増やさない**：状態が変わったときだけ通知する。

## 2. 何をしているか

```
[1 日 1 回 cron で起動（短命プロセス、リソース制限付き）]
        │
        ▼
[収集] ローカル：コンテナ状態・cgroup メモリ/swap・/proc・nginx アクセスログ・Web /_health 疎通
       クラウド：CloudWatch（EC2 指標 + アラーム）
        │
        ▼
[ルール] 決定的な判定で WARN / CRIT / INFO を算出（閾値は既存 Slack bot と統一）
         前回巡検との比較：再起動の増分、非クラッシュ再起動、ディスク増加速度と到達予測、換ページ速度
        │
        ▼
[AI]    軽量化した JSON を LLM（Gemini、Claude も切替可）へ → 総合ステータス / 異常 / 想定原因 / 推奨アクション
        │
        ▼
[出力]  JSON + Markdown レポートを EC2 に保存（14 日で自動削除）
        状態が変わったときだけ Slack へ（新規 / 解消 / AI 要約）
```

### データソース

| データソース | 答える問い |
|-------------|-----------|
| **ローカル信号**（docker / cgroup / /proc / nginx ログ / Web 疎通） | コンテナは動いているか？どれがメモリを使っているか？Web は応答するか？5xx は増えていないか？ |
| **CloudWatch**（EC2 指標 + アラーム） | AWS 側から見てインスタンスは健全か？EBS / CPU の制限に掛かっていないか？ |

→ task 要件「2 つ以上のデータソースの統合」を **ローカル信号（Sentry / PostHog の稼働状態）+ CloudWatch** で満たす。

### 既存の Slack bot との役割分担

| | 既存の Slack bot | 本プロジェクト |
|---|---|---|
| 役割 | **リアルタイム検知**（5 分ごと、閾値超過で即通知） | **日次の診断と予測**（1 日 1 回、状態変化時のみ通知） |
| 強み | 速い | 複数ソースの突き合わせ、ノイズ除去、傾向の予測、AI による原因分析 |

本プロジェクトは 1 日 1 回なので、「サービスが落ちた」のリアルタイム検知は Slack bot / CloudWatch アラームの担当とする。

## 3. これまでの成果（EC2 実測、2026-10）

単純な閾値通知では分からなかったことが分かるようになった：

- **ディスクの到達予測**：+1.3 GiB/日のペースで増加しており、**85% 到達は 2026-12 上旬、95% は 12 月末の見込み**。データ保持期間の見直しを前倒しで検討できる。
- **swap の正体**：swap 5.5 GiB の内訳をコンテナ別に特定（posthog-web 約 1.1 GiB、cymbal 約 0.7 GiB 等）。換ページ速度がほぼ 0 のため**過去の残留で、現在の性能問題ではない**と判断できた（無駄な再起動を避けられる）。
- **再起動回数の誤解を解消**：一部コンテナの累計再起動 50 回前後は、**稼働 137〜149 日間で一度も再起動していない**ことから導入初期のものと判明。
- **見えていなかった再起動**：`snuba-api` が RestartCount を増やさずに再起動されていることを検出（クラッシュではなく手動 / 定期ジョブの可能性。原因は確認中）。
- **閾値の不一致を発見**：既存 Slack bot と本スクリプトで swap 閾値・単位がずれていたのを照合して統一。

## 5. リソースとコスト

リソースに余裕の少ない EC2（m7g.xlarge：4 コア / 16 GiB、37 コンテナが大半を使用）上で動かすため：

- **短命プロセス**：起動して終わるだけ。常駐しない。ピークメモリは数十 MB。
- **依存ゼロ**：Python 標準ライブラリ + aws CLI のみ。pip / venv 不要。
- **成果物は極小**：JSON + Markdown（各数 KB）、14 日で自動削除。
- **負荷は無視できる**：docker inspect、/proc と cgroup の読み取り、数回の HTTP、CloudWatch API 2 回。
- **ハードガード**：`systemd-run -p MemoryMax=256M -p CPUQuota=50%` + `nice` / `ionice`。

**コスト**：EC2 の料金は増えない。新たな費用は LLM API（1 日 1 回、入力は数千 token 程度。有料枠でも月 1〜2 ドル以下の見込み、無料枠内ならゼロ）と CloudWatch API（ほぼゼロ）のみ。

## 6. データとプライバシー

- 収集するのは**プラットフォームの稼働データ**（コンテナ状態、ホストリソース、HTTP ステータス、nginx のステータスコードとパス）のみ。**ユーザーの個人情報・端末情報は含まない**。
- nginx のパスはクエリを除去し数字を正規化するため、`sentry_key` 等の値は残らない。
- AI に送るのも上記の集計値だけ。

## 7. セットアップ

```bash
git clone https://github.com/zixiaozh/posthog-sentry-ai-monitoring.git
cd posthog-sentry-ai-monitoring
cp .env.example .env && chmod 600 .env       # GEMINI_API_KEY と SLACK_WEBHOOK_URL を記入
sudo python3 platform_health.py --notify-test   # Slack に届くか確認
sudo python3 platform_health.py --stdout        # 実行してレポートを表示
```

- CloudWatch を使うにはインスタンスロールに [iam/cloudwatch-read-policy.json](iam/cloudwatch-read-policy.json) の権限が必要。
- 定期実行の設定、オプション、全環境変数は [SPEC.md](SPEC.md) の「7. 実行と設定」を参照。

### コード管理

- 本リポジトリ（GitHub）を正とし、EC2 は `git pull` で更新するだけの実行環境とする。
- **コミットしないもの**：`.env`（API キー・Webhook URL）、`out/`（実行成果物）。
